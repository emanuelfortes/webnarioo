Todo módulo tem o mesmo formato

Isso é deliberado: você nunca precisa procurar. Se quer saber o que a Sala grava no banco, é modules/sala/actions.ts — a mesma posição que modules/captacao/actions.ts ocupa na Captação.

Arquivo Roda onde Papel
actions.ts Servidor Mutações. Marcado com 'use server'.
queries.ts Servidor Leituras. Marcado com import 'server-only'.
components/ Navegador Interface.
hooks/ Navegador Estado de cliente. Só a Sala precisa.

As rotas em src/app/ não têm lógica: elas checam autorização, buscam dados pelas queries do módulo e montam os componentes. São oito arquivos finos, de 367 linhas no total.

A fronteira que organiza tudo

Uma única decisão explica o desenho acima e fecha o achado mais grave da auditoria.

O navegador não escreve no banco.

core/db/server.ts carrega a service_role key e começa com import 'server-only'. Se qualquer componente de cliente importar esse módulo, o build falha — a garantia é mecânica, não depende de ninguém lembrar.

core/db/browser.ts carrega a anon key, cujo único poder no RLS é select em messages, o mínimo para o realtime do chat funcionar.

E toda ação de /admin e /dashboard passa por exigirAdmin(), que valida um cookie httpOnly assinado. Não é mais condicional de renderização em React: chamar a API direto não contorna nada.

Por que o Supabase continua no projeto

Por duas coisas, e só: Realtime (o chat) e Presence (o contador de espectadores). Função serverless não segura conexão aberta pelos 75 minutos de uma sessão, e Postgres puro não faz broadcast. O banco em si já poderia ser trocado sem tocar em nenhum módulo — todo o acesso está concentrado em queries.ts e actions.ts. É esse isolamento que deixa a porta aberta para o Neon numa etapa futura, se você quiser.

O que mudou

Antes

  • SPA Vite, tudo no navegador
  • Anon key escrevendo direto no Postgres
  • Login como condicional de render
  • Schema e RLS fora do repositório
  • Landing carregando em branco
  • Identidade do lead inventada no cliente
→

Depois

  • Next.js App Router, servidor + cliente
  • Service role só no servidor
  • Cookie httpOnly assinado, verificado
  • supabase/schema.sql versionado
  • Landing renderizada no servidor
  • Identidade emitida pelo servidor

O que ficou em aberto

Três itens, e os motivos são diferentes em cada caso.

Testes e CI — o mais importante da lista

Continua valendo o que a auditoria dizia: a lógica central deste sistema é temporal — relógio da sessão, sincronia do vídeo, marcos de retenção, corte das mensagens programadas — e é exatamente o tipo de código que não falha em desenvolvimento e falha em produção, com a sala cheia. Vários dos bugs corrigidos aqui (A2, A3, M1) morreriam num teste de dez linhas.

Revisão jurídica da política de privacidade

A página /privacidade descreve com precisão o que o sistema realmente coleta — foi escrita a partir do código, não de um modelo. Mas faltam a razão social, o CNPJ e o e-mail do encarregado, que só você tem, e uma revisão de quem entende do assunto.
